# @supabase/postgrest-planner

Upstream PostgREST (v16.4) request planner compiled to a WASI reactor (`dist/postgrest-planner.wasm`), plus a typed Node host. Given a PostgREST schema cache, an optional supplementary catalog and a request (`method`, `url`, `headers`, `body`), it returns a plan description (action, selected columns and types, embeds, mutation or rpc details, the shape of the result) or the exact upstream error (`PGRST…`). Private for now.

## Usage

```ts
import { loadPlanner, parseConfigDump } from '@supabase/postgrest-planner'

const planner = await loadPlanner() // or { wasmPath }
const loaded = planner.load({
  config: parseConfigDump(configDump),
  schema: schemaJson,
  supplementary, // optional, see below
})
if (loaded.ok) {
  const plan = planner.plan(loaded.handle, { method: 'GET', url: '/users?select=username' })
  planner.freeCache(loaded.handle)
}
```

Reactor errors (`ok: false`) are returned as values; only host failures (missing wasm, trap) throw.

The wasm is not committed. Build it with:


Prerequisites: the [supa-wasm](https://github.com/supabase/supa-wasm) toolchain checked out locally (read-only use): wasm GHC 9.10, the cabal store, wasm libpq, vendored PostgREST at `v16.4` and its Hackage patches. Environment overrides: `SUPA_WASM` (default `/Users/jgoux/Code/supabase/supa-wasm`), `GHC_WASM`, `CABAL_DIR`, `PLANNER_WORK` (cabal work dir, default `dist/work`). A cold build compiles the whole PostgREST dependency tree and takes a long while; later builds are incremental. `haskell/src/Planner/BuildInfo.hs` is generated by `build.sh`.

## ABI (version 2)

All payloads are UTF-8 JSON in linear memory; results are a pointer to `[u32 LE length][bytes]`.

- `planner_alloc(n) -> ptr`, `planner_free(ptr)`: host-owned input buffers and results
- `planner_info() -> res`: `{abi, postgrest:{version,tag,commit}, ghc}`
- `planner_load(cfgP, cfgN, schP, schN, suppP, suppN) -> res`: config is a JSON object of PostgREST keys, schema is `--dump-schema` output, the last pair is the supplementary catalog (`0, 0` for none; the buffer is copied, the host keeps ownership). Returns `{handle, schemas, summary, ignoredConfigKeys, degraded, columnOrderKnown}`
- `planner_dump(handle) -> res`: schema cache re-encoded with upstream `ToJSON`
- `planner_free_cache(handle)`
- `planner_plan(handle, reqP, reqN) -> res`: plan description or upstream error

ABI 2 differs from 1 by the second buffer pair of `planner_load`, the `degraded` and `columnOrderKnown` fields of its result, and the `form`, `shape`, `rpc`, `filters` and `degraded` fields of a plan. The abi 1 summary fields of a plan (`select`, `embeds`, `mutation`, `routine`, ...) are unchanged.

## Supplementary catalog

The schema dump loses facts the planner needs to describe a result: the dump decoder cannot keep the order of the columns of a table (JSON objects), and the dump has neither the computed fields' return types nor foreign key validity or the `OUT` columns of a function (a routine's volatility is in the dump, and is what a plan reports). One JSON document supplies them (`Supplementary` in `src/index.ts`, `format: 1`):

| key                   | content                                                                                                                                                         |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `relations`           | `{schema, name, columns: [{name, attnum}]}` for every table, view, matview, partitioned/foreign table                                                           |
| `composites`          | `{schema, name, attributes: [{name, type, attnum}]}`                                                                                                            |
| `foreignKeys`         | `{schema, table, constraint, validated}` (`pg_constraint.convalidated`)                                                                                         |
| `functions`           | `{schema, name, argTypes, volatility, defaults, returns: {kind, setof, type}, outColumns}`, exposed schemas                                                     |
| `searchPathFunctions` | same, for the schemas of `db-extra-search-path` that are not exposed, and the extension members of any covered schema (below)                                   |
| `types`               | `{schema, name, kind, base, element}` for every user type (domain, enum, composite, range...) and array type of a covered schema; `element` is set for an array |
| `schemas`             | the schemas the catalog covers: the exposed ones plus `db-extra-search-path`                                                                                    |
| `casts`               | `{source, target, method}` for every `pg_cast` row with a side outside `pg_catalog` (`method`: `f`, `i`, `b`)                                                   |

A name is never read as an array by its spelling: the array of a builtin type is named by `pg_catalog` after its element's `pg_type` name (`_int4`, `_text`), so `x::_int4` is `int4[]` while `x::_integer` or `x::_bigint` name no builtin and resolve along the search path like any other name (a domain `public._integer` is what the first means, and without one the cast is unresolved with a `cast-type:` note, where PostgreSQL refuses it). A user array type is listed under its own `pg_type` name (`_name`, or what Postgres made of it when that name was taken) with its `element`, and a cast name resolves to it at the schema of the search path that has it (`x::_d` is `a._d`, the array of `a.d`, on the path `a,b` even when `b` has a domain named `_d`). Types are keyed by their `(schema, name)` as `pg_type` holds them, and every type spelling the planner reads (`format_type` quotes an identifier only when it needs it: `public."Amount"`) is parsed back into that pair, so a quoted name and its pair are one type.

`functions` leaves out the members of an extension (an exposed schema is not the place to look for what an extension installs), but a lookup must not skip them: `extensions.label(t)` hides `personal.label(t)` on the path `extensions,personal`. So `searchPathFunctions` lists the extension members of every covered schema that a lookup can reach, those with one row type as their first argument and no other argument without a default (a computed field or relationship) or with `OUT` columns, and not the hundreds of others (`postgis` alone installs hundreds). The mapper does not print them in its `Functions`, which is built from `functions` alone: it has always left them out, to keep what an extension installs out of the project's generated API.

An `OUT` column without a name is named `column1`, `column2`, ... by its position among the output arguments, as Postgres names the key of the result (`f(a int, OUT int, OUT text)` answers `{"column1": 1, "column2": "x"}`). A function with one output column and no name for it is a scalar function for the call (upstream aliases it `pgrst_call`, which Postgres takes as the column name): `f(OUT integer)` answers `{"pgrst_call": 7}`, and the catalog names the column so. A function that returns a composite type, or a domain over one, has `kind: composite` whatever its `OUT` columns are: the row is expanded (`f(OUT u users)`, or `u` of a domain over `users`, answers the columns of `users`).

A computed field is a function `name(relation)` whose other arguments, if any, all have a default (`defaults` is `pg_proc.pronargdefaults`): PostgreSQL calls `label(t)` on `a.label(t, n int DEFAULT 0)` too. The first schema of the path with such a function decides, even when a later schema has a function of the row alone (`a.label(t, n int DEFAULT 0)` text hides `b.label(t)` integer on the path `a,b`), and two of them in that schema (`a.label(t)` with `a.label(t, n int DEFAULT 0)`) are ambiguous: PostgreSQL finds no column, so the field is unresolved with a `computed-field:` note.

`schemas` is the coverage record. A computed field and a cast name are looked up along the search path of the request (its schema, then `db-extra-search-path`), and the lookup can only prove a name absent from a schema the catalog covers: a path schema off `schemas` (no catalog, or one generated for another extra search path) stops the lookup there, and the field or cast is unresolved with a `computed-field:` or `cast-type:` note instead of resolving to a later schema. A hit in an uncovered schema is still a hit.

The decoder is lenient on purpose: unknown keys are ignored at every level and a missing section is an empty one, so the producer may store more in the same document (view definitions, function bodies, CHECK constraints). A document that is not JSON, or with another `format`, fails the load with `PLANNER_BAD_SUPPLEMENTARY`.

`test/fixtures/supplementary.sql` is the generator; the fixture is the output for the test database (`db-schemas` must match the list in the SQL, and `extra_search_path` the `db-extra-search-path` of the config; `supplementary-search-path.json` is the same query with `{public,extensions,cast_a,cast_b,cast_c,arr_a,arr_b,ext_owned}`). To regenerate it with the shared test database running:

```sh
DOCKER_CONTEXT=orbstack docker exec -i supabase_db_test psql -q -U postgres -At \
  -v 'extra_search_path={public,extensions}' -f - \
  < test/fixtures/supplementary.sql > test/fixtures/supplementary.json
```

With a catalog the columns of every listed table are put in `attnum` order when the handle is loaded, so a `*` that upstream expands itself (next to an aggregate) comes out in the order a PostgREST loaded from the database would use.

### Degraded mode

Without a catalog everything still plans, but what the planner had to guess is listed in `degraded`, never silently assumed:

| note                                          | where      | meaning                                                                          |
| --------------------------------------------- | ---------- | -------------------------------------------------------------------------------- |
| `no-supplementary-catalog`                    | load       | no catalog was given                                                             |
| `column-order:<schema>.<relation>`            | load, plan | the relation has no `attnum` order: `*` is in the dump's order, not the table's  |
| `computed-field:<relation>.<name>`            | plan       | no catalog to tell whether `<name>` is a computed field: field is unresolved     |
| `fk-validation:<schema>.<table>.<constraint>` | plan       | no catalog entry says whether the key is validated: a to-one on it is not proven |
| `rpc-columns:<function>`                      | plan       | an RPC returns a composite type or `RETURNS TABLE` the catalog does not describe |
| `rpc-embed-relation:<schema>.<relation>`      | plan       | upstream resolves the embeds of an RPC against another relation (see RPC)        |
| `cast-type:<name>`                            | plan       | a cast names a type the catalog does not mention: the field is unresolved        |
| `media-handler:<schema>.<function>`           | plan       | the negotiated media handler is a custom function: the body is unknown           |

`columnOrderKnown` in the load result is `true` when no relation lacks its order.

## Result shape

A plan carries, next to the abi 1 summary:

- `form`: what the body looks like. `rowset` for reads, for mutations that return the representation and for RPC that return a set of composite rows, `none` for mutations without `Prefer: return=representation`, `single-scalar`, `setof-scalar` and `single-composite` for RPC, `null` for plans that return no rows of a relation, and for a plan whose media handler is custom (see below).
- `shape`: `{relation: {schema, name}, fields, embeds}` for the root relation of reads (GET, HEAD), of mutations with `return=representation` and of RPC that return composite rows; `null` otherwise (including the scalar RPC forms). `embeds` is described below.
- Empty select of a mutation. `DELETE /t?select=` (or `PATCH`, `POST`) with `return=representation` is read as `*` of what the statement returns, not of the table: upstream adds the primary key to the `RETURNING` (as a set of names, so in the order of their names, not of the key), and a table without a key gets `RETURNING 1`. `fields` is that key (`[{"id":2}]`), or the one field `?column?` (`int4`, not null, `unresolved` provenance) for a table without one.
- `rpc`: `null` unless the plan is a `/rpc/*` call, see below.
- Custom media handlers. A table's `*/*` handler (default select only), a handler of `application/json` or any other media type that is not one of the builtins overrides upstream's JSON aggregate (`Negotiate.hs`; the vnd.pgrst types cannot be overridden): the body is whatever the function returns, so the plan has `form: null`, `shape: null` and the note `media-handler:<schema>.<function>`, and no other note about the shape. `filters` and `rpc` are reported as usual.
- `filters`: the target of every filter parameter, see below.
- `degraded`: the notes above that apply to this plan.

Every entry of `fields` is `{name, pgType, nullable, provenance, baseType?}`, in the order PostgREST emits the columns:

- `name`: the alias, else the aggregate's lowercased name (`count`, `sum`, ...), else the last JSON key (`data->a->>b` is `b`), else the column name. The `outputName` of the plan's `select` items is the same name (`price.sum()` is `sum`, `count()` is `count`).
- `pgType`: normalised spelling: internal names (`int4`, `timestamptz`), no type modifiers, `schema.name` outside `pg_catalog`, `[]` for arrays; `null` when unresolved. `baseType` is the base type of a domain, only when it differs.
- `nullable`: a column is nullable unless declared `NOT NULL`; a JSON path always is; `count` is never; other aggregates always are; a cast keeps the nullability of what it casts only for the pairs known not to return `NULL` for a non-null input: the same type, numeric to numeric (`int2`, `int4`, `int8`, `numeric`, `float4`, `float8`: they raise instead), a builtin type to `text`, `varchar` or `bpchar` (output functions), and the text family and `name` among themselves; a user type (domain, enum, composite, extension type) keeps it only to itself or to `text`, `varchar` or `bpchar`, and only when the catalog's `casts` lists no cast function for that exact pair (PostgreSQL prefers a `CREATE CAST ... WITH FUNCTION` to the output function, and that function may return `NULL`; a domain is cast like its base type; with no catalog, or one without `casts`, a user type is nullable); every other cast is nullable (`timestamptz::time`, `timestamp::time` and `timestamptz::timetz` return `NULL` for `infinity`); a computed field always is. These proofs assume the casts between `pg_catalog` types are the ones `pg_catalog` ships: overriding one means owning a `pg_catalog` type, which takes a superuser, and a Supabase project has none. A computed field `name` of a relation is the function `name(<relation>)` that Postgres finds through the search path of the request (its schema, then `db-extra-search-path`): of the functions with that name and argument, the one in the first schema of the path is the field's (the catalog lists the functions of the exposed schemas and of `db-extra-search-path`, those that belong to an extension included, since upstream does not tell them apart); a function of a schema off the path is not visible and the name is unresolved, and so is a name for which the lookup reaches a path schema the catalog does not cover. An aggregate over a domain is typed on its base type (`sum` of a domain over `int4` is `int8`). That holds for a computed field returning a domain whose base type the catalog knows (a column of the domain shows it; a domain nothing else mentions stays `schema.name`). `min` and `max` are typed as Postgres resolves them, not always as the input: `varchar`, `name` and `"char"` give `text`, `cidr` gives `inet`, the `reg*` types give `oid`, arrays, enums and the types with their own variant keep their type, and a `pg_catalog` type with neither a variant nor a coercion (`uuid`, `bool`, `json`, `bytea`, ranges, ...) has no `min`/`max` (Postgres fails the request with `42883`): the field is unresolved (`pgType: null`, provenance `unresolved`). The second cast of a select item (`id::text::int4`) applies only after an aggregate: upstream drops it otherwise. A JSON path is `json` only when upstream reads a `json` column as it is; every other type, a domain over `json` and the attributes of a composite type or `OUT` columns included, goes through `to_jsonb` and is `jsonb`.
- `cast` target: the cast name is pasted unquoted into the SQL, so it is folded to lower case and has no schema or `[]`. It resolves the way Postgres does, along the search path of the request (its schema, then `db-extra-search-path`) with `pg_catalog` first unless the path names it (an explicit `pg_catalog` keeps its position, so a `public.int4` domain ahead of it wins over the builtin `int4`); the SQL spellings the grammar maps to builtin names (`int`, `integer`, `double precision`, `character varying`, ...) always mean the builtin. A name resolves to a builtin type (or its `_int4` array spelling) or to a user type of a schema that the catalog covers, where it lists every user type, used or not; the result is spelled `schema.name`. A path schema the catalog does not cover cannot be skipped: the cast is unresolved. Any other name is unresolved (`pgType: null`, provenance `unresolved`, note `cast-type:<name>`): the type may exist, the planner does not invent it, and upstream still plans the request.
- `provenance`, nested through `of`: `plain` (`source: {schema, relation, column}`, and `functionRows: true` for a column read from the rows of a function), `computed`, `jsonPath` (`path` of `->`/`->>` steps with `key` or `index`), `cast` (`to`), `aggregate` (`function`), `representation` (data representation, untested: the fixture has none), `outColumn` (`function`, `column`: an `OUT` or `RETURNS TABLE` column of an RPC), `compositeAttribute` (`type`, `attribute`: an attribute of the composite type an RPC returns) or `unresolved` (`reason`; neither a column nor a computed field of the relation).
- `reason`: `function-rows` on the fields of the rows of an RPC, see below.

Select items are evaluated the way upstream prints them: expression (column, JSON path), field cast, aggregate, aggregate cast.

### RPC

`rpc` is `{function: {schema, name}, volatility, source}` for a `/rpc/*` plan. Dispatch is upstream's: an unknown function is `PGRST202` and an overload the arguments cannot choose between is `PGRST203`, both a top-level `ok: false`; `GET`, `POST` and the other methods are as upstream accepts them (`DELETE` is `PGRST101`).

| return type                                     | `form`                                         | `shape`                                       | `source`                                                                          |
| ----------------------------------------------- | ---------------------------------------------- | --------------------------------------------- | --------------------------------------------------------------------------------- |
| a scalar (`void` included)                      | `single-scalar`                                | `null`                                        | `null`                                                                            |
| `setof` a scalar                                | `setof-scalar`                                 | `null`                                        | `null`                                                                            |
| a table or view row, composite                  | `single-composite`                             | the relation's columns, `*` in `attnum` order | `{kind: relation, schema, name, view}` or `{kind: composite, schema, name}`       |
| `setof` a table, view or composite              | `rowset`                                       | the same                                      | the same                                                                          |
| `RETURNS TABLE (...)`, `OUT`, `INOUT`, `record` | `rowset` (`single-composite` when not `setof`) | the columns, relation `pg_catalog.record`     | `{kind: returnsTable, columns: [{name, pgType}]}`, from the supplementary catalog |

`volatility` is `immutable`, `stable` or `volatile`, read from the schema dump (`pdVolatility`, the value upstream picks the transaction mode with; the supplementary catalog's copy is not used). Upstream does not refuse a `GET` of a volatile function, Postgres does when it runs.

Function rows. A function can return rows its relation's constraints would refuse (a view-like `select`, a row built by hand), so every field read from the rows of an RPC is `nullable: true` with `reason: function-rows`, whatever the column says. The reason survives a cast (it keeps the nullability of what it casts) and not a JSON path or an aggregate, which are nullable on their own. The `plain` provenance of such a column carries `functionRows: true`, and it stays there under the `of` of a cast, a JSON path or an aggregate, so a printer can tell that the value comes from function rows (and that its table's constraints, a JSON Schema derived from a `CHECK` for one, do not hold for it) after the reason is gone. A first-level to-one embed of the rows (not under another embed, not `!inner`) is nullable with reason `function-rows` and keeps `fkProven` and its `relationship.columns`: a printer that traces a `STABLE` or `IMMUTABLE` function down to the table can restore the embed when the key proves it. An `!inner` embed stays non-null (a missing row drops the parent), embeds deeper than the first level follow the usual rules. The rows of a computed relationship (`setof` or not) are function rows as well: the function is called directly, not through the table, so its fields and its first-level to-one embeds are `nullable` with reason `function-rows` (the embed keeps `fkProven`), while `!inner` embeds and the embed's own nullability keep their rules; a filter on a column of its rows reports `function-rows` too.

Bare `count`. Upstream parses `count` (no parentheses) as a field. Postgres reads `<table>.count` as the function `count(<table>)`, the aggregate over the rows, when the table has no column or computed field of that name, so `messages(count)` is `count()`: `int8`, never null, provenance `aggregate`. It needs the supplementary catalog to rule a computed field out. No other aggregate name works this way, and neither does a bare `count` with a JSON path.

One column. A single `OUT`, `INOUT` or one-column `RETURNS TABLE` is a composite of that column for upstream (`f(INOUT n int)` answers `{"n": 3}`): it is read from the catalog like the other `OUT` columns, under the relation `pg_catalog.record`.

Unknown columns. When the catalog does not list the composite type or `OUT` columns, the plan carries `rpc-columns:<function>` and the selected names have an `unresolved` provenance (no catalog at all: a `RETURNS TABLE` function is in this case; a function returning a table or view is not, the dump has its columns).

Upstream quirk. For the embeds of an RPC upstream resolves the relationship against `<schema of the function>.<name of the returned table>` (`Plan.hs` `callReadPlan`, `QI pdSchema (funcTableName proc)`), not against the table the function returns: a function in `public` that returns `personal.users` reads `public.users`, and `record` finds no relation (`PGRST200` for any embed). The planner reports the embeds as upstream plans them and adds `rpc-embed-relation:<schema>.<relation>`, naming the relation the function really returns, whenever an RPC has embeds and upstream resolves them against another relation. `shape.fields` always come from the returned type.

### Filters

`filters` has one entry per filter parameter, in the order upstream applies them: node by node (root first, then the embeds in the order of the select), and within a node the `and=` / `or=` trees, then the column filters, then the embed tests. For a mutation the filters of the mutated table come first. Upstream parses `or=` and `and=` (also `not.or=`, nested groups and `embed.or=`): every leaf is an entry of `filters`, whose `logic` lists its enclosing groups, outermost first (`[{operator: 'or', negated: false}, {operator: 'and', negated: false}]`). On a mutation upstream also puts every logic tree on the root's `where_`, including the ones written for an embed (`users.or=...`); the planner reports each one only where it was written (the embed) and not against the mutated table.

Non-operator `GET` parameters of an RPC are arguments, not filters (`filters` stays empty for them).

| `kind`   | keys                                                                                               | meaning                                                                          |
| -------- | -------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| `column` | `embed`, `column`, `jsonPath`, `pgType`, `baseType?`, `nullable`, `reason?`, `provenance`, `logic` | `col=op.value`, `col->a->>b=op.value`, `embed.col=op.value` or a leaf of a tree  |
| `embed`  | `embed`, `column`, `tested`, `negated`, `logic`                                                    | `embed=is.null` and `embed=not.is.null`, where `embed` is an embed of the select |

`embed` is the path of keys (alias, else name) from the root of the embed the filter is written under (`[]` for the root). A `column` entry is resolved as a select item is: `pgType`, `nullable` and `provenance` are those of the column before its JSON path (`jsonPath` is the same `key`/`index` steps as in a field), a column that does not exist gives `pgType: null` and an `unresolved` provenance (a filter on it fails in Postgres, not in the planner), and the columns of the rows of an RPC root carry `reason: function-rows`. An `embed` entry is what upstream rewrites into a join test: `embed=is.null` and `embed=not.is.null` (with the name of an embed of the select) only; `tested` is the embed it tests (`embed` followed by `column`) and `negated` is `not.is.null`. `is.not_null` and every other operator are not rewritten: they are `column` entries on the name.

There is no per-filter error. A filter written under an embed the select does not name (`channels.slug=eq.x` without `channels(...)`) is `PGRST108` upstream and fails the whole request, so the whole plan is `ok: false` with that error.

### Embeds

`shape.embeds` has one entry per embedded relation, in the order PostgREST emits them (after `fields`), recursively: every entry carries its own `shape` (`{relation, fields, embeds}`), with `*` expanded in `attnum` order against the relation the embed really reads (also for computed relationships). Reads and mutations that return the representation have the same contract.

| key               | content                                                                                                                                                                  |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `name`, `alias`   | the embedded relation and alias as written                                                                                                                               |
| `key`             | the JSON key in the parent row (alias, else name); `null` for a spread and for an empty embed (`rel()`)                                                                  |
| `spread`, `empty` | `...rel(...)`, `rel()`: an empty embed is only there to filter or order, it has no key and no `outputs`; its `shape` is still given                                      |
| `path`            | identity: the keys of the embeds from the root down to this one (spreads included)                                                                                       |
| `outputs`         | the keys this embed adds to the result, each a path from the root row: `[key]` for an embed, the merged field keys (and those of the embeds a spread nests) for a spread |
| `join`            | `inner` for `!inner`, else `left`                                                                                                                                        |
| `cardinality`     | `one` (object) or `many` (array)                                                                                                                                         |
| `relationship`    | `{kind: m2o\|o2o\|o2m\|m2m\|computed, fkSide: origin\|target\|null, constraint, columns: [{from, to}], junction, function}`; `from` is on the parent, `to` on the embed  |
| `target`          | `{schema, name, kind: table\|view\|function}`: the relation the embed reads; `function` when it is reached through a computed relationship (`relationship.function`)     |
| `nullable`        | whether the embedded value can be null, with the `reason` below                                                                                                          |
| `fkProven`        | a to-one the foreign key proves: many-to-one (or the owning side of a one-to-one) between two tables, key columns all NOT NULL, constraint validated                     |

`nullable` of a to-one, first match wins:

| `reason`                                                                                                                                | `nullable` | when                                                                                                                                                                                                                                                                      |
| --------------------------------------------------------------------------------------------------------------------------------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `array`                                                                                                                                 | `false`    | to-many (never null, `[]` when empty)                                                                                                                                                                                                                                     |
| `inner-join`                                                                                                                            | `false`    | `!inner`: a missing match drops the parent row                                                                                                                                                                                                                            |
| `single-composite`                                                                                                                      | `false`    | a computed relationship to a function that returns one composite (not `setof`): Postgres yields a row of NULLs when nothing matches. Its fields are the rows of a function: `nullable`, reason `function-rows`; a filter, a `!inner` child or the rules above still apply |
| `write`                                                                                                                                 | `true`     | the plan is a mutation: every left-joined to-one is nullable (`fkProven` is still computed)                                                                                                                                                                               |
| `computed`, `inverse-o2o`, `view-origin`, `view-target`, `nullable-fk-column`, `fk-not-validated`, `fk-unknown`, `unknown-relationship` | `true`     | the key does not prove the row (`fkProven: false`); `fk-unknown`: no catalog entry says whether the key is validated, and the plan notes `fk-validation:...`                                                                                                              |
| `filtered`                                                                                                                              | `true`     | a filter, an offset or a limit of 0 on the embed can drop its row                                                                                                                                                                                                         |
| `nested-inner`                                                                                                                          | `true`     | a direct child joined with `!inner` drops this row when it has no match                                                                                                                                                                                                   |

Spreads. A to-one spread merges its fields into the parent row: `shape.fields` are those merged keys, `nullable` is the nullability of the join, and every merged field (and every embed nested in it, reason `spread-parent`) is nullable when the spread is. A to-many spread gives one array per field: `shape.fields` describe the elements, the array itself is never null (`nullable` is `false`, `array`) unless it is merged by a nullable to-one spread. Upstream rejects aggregates in a to-many spread (`PGRST127`). The aggregates of a to-one spread inside another spread are applied by upstream at the nearest ancestor that is not a spread; the planner puts each back on the field that wrote it, so `...a(x, ...b(m:y.max()))` types `m` as the aggregate (`count` is never null, the other aggregates always are). Nested embeds below a to-many spread are inside the array as well: the key holds one value per element.

A failure upstream reports (an unknown embed, `PGRST108` for a filter on an embed that is not selected, `PGRST200`, ...) makes the whole plan `ok: false` with upstream's error.
